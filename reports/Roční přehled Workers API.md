# Annual Changes Expose Lopata's Remaining Gaps

**PR #31 implements four useful backports, but it does not complete compatibility with the Workers changes published from October 5, 2025 through October 5, 2026.** The immediate review blocker is its new validation of shared `exports` configuration: valid Durable Object and Workflow declarations are rejected as non-Worker exports. The highest-value follow-ups concern Workflow checkpoint correctness, Queue and Email results, modern tracing and WebSocket behavior, Durable Object alarms, and local configuration resolution. Larger gaps remain in Dynamic Worker capability transfer, Browser Run's direct binding, and the Container primitives required by Sandbox SDK 1.0. These are user-code and local-development contracts, distinct from cloud billing, geography, inference infrastructure, and hosted dashboards. The research screened **388 official changelog entries across 32 product folders** and **127 compatibility-flag source files, with 46 in-window introduction/default changes**; these figures measure source coverage, not exhaustive API conformance. Findings below distinguish a demonstrated PR regression, pre-existing defects, missing annual contracts, older or undated contracts, and behavior that still needs a targeted check. ([PR #31](https://github.com/contember/lopata/pull/31); [official changelog snapshot](https://github.com/cloudflare/cloudflare-docs/tree/03f58703df62daa18049b7e0043bb6e25c659670/src/content/changelog); [official flag snapshot](https://github.com/cloudflare/cloudflare-docs/tree/03f58703df62daa18049b7e0043bb6e25c659670/src/content/compatibility-flags))

## Configuration adds one PR regression and several startup gaps

### Shared declarations must coexist with cache exports

**The only newly introduced defect established by the research's base comparison is unconditional Worker-only `exports` validation.** Cloudflare published declarative DO lifecycle exports on **July 4, 2026**, Workflow exports on **September 24**, and Workflow `ctx.exports` access on **September 27**. Lopata types `exports` as Worker entries and validates every configuration, even when caching is absent. A valid temporary `exports.MyWorkflow = { type: 'workflow', name: 'my-workflow' }` config failed with `exports.MyWorkflow.type must be "worker"`; the same branch rejects `durable-object`. This is a PR review blocker independent of whether the full new declaration model is implemented. ([DO declaration announcement](https://developers.cloudflare.com/changelog/post/2026-06-30-declarative-do-class-exports/); [Workflow declarations](https://developers.cloudflare.com/changelog/post/2026-09-24-workflow-exports/); [Workflow loopbacks](https://developers.cloudflare.com/changelog/post/2026-09-27-workflow-ctx-exports/); [src/config.ts:8–9,110–143][config]; [PR comparison](https://github.com/contember/lopata/compare/99ae836125d56f34d97a007563f7cb4ac21866b5...8b82801ac83d4880d64a0cfa948698347ea84f1a))

Accepting the types alone would not close the annual gap. Env construction applies legacy DO migrations and creates Workflows from `config.workflows`; thread construction does likewise. Loopbacks select only classes branded as `lopata.WorkerEntrypoint`. The declaration model's local class/storage lifecycle, Workflow limits/retention/schedules, and Workflow loopbacks therefore need separate wiring. Account-wide class transfer coordination remains hosted platform behavior. Existing cache tests prove WorkerEntrypoint loopbacks and reject arbitrary types, but omit coexistence with the official DO/Workflow types. ([src/env.ts:141–201][env]; [src/worker-thread/thread-env.ts:96–104][thread-env]; [src/bindings/worker-cache.ts:627–645][worker-cache]; [tests/worker-cache-config.test.ts:34–47,69–117](https://github.com/contember/lopata/blob/8b82801ac83d4880d64a0cfa948698347ea84f1a/tests/worker-cache-config.test.ts#L34-L117))

## Runtime compatibility depends on semantics and every entry path

### Tracing coverage is smaller than the public namespace suggests

Cloudflare introduced custom spans on **June 16, 2026**, manual active spans on **July 28**, and `startSpan`, `getActiveSpan`, `recordException`, `setAttributes`, and chainable setters on **September 25**. Lopata's public namespace exposes only `enterSpan`; its handle has `setAttribute` and an always-true `isTraced`, with no public `end`. The internal callback runner named `startSpan` is not Cloudflare's public `tracing.startSpan(name): Span`. Missing methods are high-confidence annual omissions. ([June launch](https://developers.cloudflare.com/changelog/post/2026-06-16-custom-spans/); [July extension](https://developers.cloudflare.com/changelog/post/2026-07-28-start-active-span/); [September extension](https://developers.cloudflare.com/changelog/post/2026-09-25-custom-span-apis/); [src/tracing/span.ts:16–21,127–150][span])

The existing method is also partial against the current contract: `setAttribute` returns `undefined` rather than the same span; `enterSpan` does not forward trailing callback arguments; manual end, post-end annotation suppression, idempotence, and root-span lookup are absent. The documented 64-byte name and approximately 64 KB attribute/exception-data bounds are not implemented in the inspected runner. These current-reference semantics are established, but the first release date of every detail is not independently known. The docs explicitly say `spanContext()` and `setStatus` are not yet available, so neither belongs in a shipped-API backlog. ([current custom-span contract](https://developers.cloudflare.com/workers/observability/traces/custom-spans/); [src/tracing/span.ts:44–76,138–150][span])

**Backend wiring makes even June support partial.** The runtime notes correctly identify an imported Bun namespace and an in-process `ExecutionContext.tracing`, but that does not establish the normal CLI handler path. The configuration researcher traced `WorkerExecutionContext`, which lacks `tracing`; `worker-thread/entry.ts:227–231` supplies it to the dispatcher, and `WorkerDispatcher.attachContext` adds only cache/exports. Vite's generated module also lacks the named `tracing` export. Thus import-based Bun support, in-process context support, normal Worker-thread context support, and Vite import support have different coverage. This resolves the apparent disagreement between the notes without asserting an unperformed Vite build failure. ([src/virtual-modules.ts:44–52][virtual]; [src/execution-context.ts:24–34][context]; [src/worker-thread/execution-context.ts:31–56][thread-context]; [src/worker-thread/entry.ts:227–231][thread-entry]; [src/bindings/worker-cache.ts:593–605][worker-cache]; [src/vite-plugin/modules-plugin.ts:44–81][vite-modules])

## Cloud-only changes and uncertain dates need different conclusions

Cloud billing, account quotas, compute/storage geography, hosted resource dashboards, inference capacity, global CDN propagation, managed container placement, and edge TLS/transport measurements are not intrinsically local APIs. Surveyed R2/D1 announcements chiefly concern these areas, rather than newly missing object or prepared-statement methods. ### Verification establishes source omissions and selected observed failures

Researchers inspected owner code, callers/construction paths, and existing test source at the pinned head. Lightweight probes used **Bun 1.3.14**, reproducing valid-export rejection, required-secret filtering/shell-only omissions, `CLOUDFLARE_ENV` omission, minimal-KV write failure, SQL path imports, Error own-field loss, and direct WebSocket pair behavior. They also confirmed narrowly native-supported iterable Response bodies and Performance-global availability. **No full test suite, live Cloudflare/workerd conformance run, Docker/Sandbox scenario, browser launch, remote inference/indexing, or Code Mode/Dynamic Workflows end-to-end run was performed for this annual review.** No implementation or PR changes were made. ([configuration probe record](../research_notes/Roční%20přehled%20Workers%20API/config-and-coverage.md); [runtime probe record](../research_notes/Roční%20přehled%20Workers%20API/runtime.md); [binding methodology](../research_notes/Roční%20přehled%20Workers%20API/bindings.md))

The PR background separately reports **Bun 1.4.2** CI-compatibility checks with 1,885 passes, zero failures, two skips, and successful lint/format/type checks. Those results were **not independently rerun** by the annual researchers and do not validate APIs absent from the tests. In particular, Bun 1.3.14 native/SQL observations must not be generalized to Bun 1.4.2 without another probe. The available local workerd reference checkout was dated March 12, 2026; it cannot establish that a later API was absent from Cloudflare. Current unpinned workerd declarations are corroboration, not date authority. ([repository verification:118–137][background]; [runtime limitations](../research_notes/Roční%20přehled%20Workers%20API/runtime.md))

## Conclusion

The most useful next compatibility milestone is **a complete vertical contract across parsing, env construction, user-worker execution, Vite modules, transport, and replay**, rather than a longer list of binding names. Existing building blocks explain why many gaps are tractable, but their presence can conceal real failure modes: first-run streams without replay, stored emails without results, imported Node modules with excessive permissions, and declared options that never reach the child runtime. A focused correction to shared export validation is immediately separable from that larger work.

Future support claims should name the exercised backend, runtime version, compatibility-date/flag setting, and observable behavior. The source inventory is broad enough to prioritize work now; it is not a reason to add shims for already native-supported APIs or to claim full annual conformance. The decisive checks are narrow application-path cases for documented results, bytes, lifecycle, and persisted identity, followed by targeted SDK scenarios where the underlying capability transport actually supports them.
