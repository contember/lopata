# Workers configuration/platform review and annual coverage index

## 1. Which configuration and platform changes matter to Lopata PR #31?

### Takeaway

The current PR implements four selected backports, but the annual official changelog reveals additional local configuration contracts. The most important PR-specific issue is that Workers Cache validation treats the shared `exports` configuration as Worker-only and rejects valid Durable Object and Workflow declarations. Several older local-dev additions also remain unsupported.

Reviewed checkout: PR #31 head `8b82801ac83d4880d64a0cfa948698347ea84f1a`, branch `feat/cloudflare-workers-backports`. The checkout matched GitHub's PR head when inspected. GitHub's PR base was `99ae836125d56f34d97a007563f7cb4ac21866b5`; local `origin/main` and the merge base matched it. The base-to-head config diff confirms that unconditional `exports` validation is newly introduced by this PR. Review interval: **2025-10-05 through 2026-10-05 inclusive**. Existing `CLOUDFLARE-COMPATIBILITY.md:3` covers only April 2–October 2, 2026. [PR](https://github.com/contember/lopata/pull/31); [config diff](https://github.com/contember/lopata/compare/99ae836125d56f34d97a007563f7cb4ac21866b5...8b82801ac83d4880d64a0cfa948698347ea84f1a); [existing review][compat-review].

Priority means implementation/review urgency, not a claim of a production security incident: **P1** = startup blocker or PR-introduced valid-config rejection; **P2** = useful local contract or behavioral mismatch; **P3** = optional tooling/platform expansion. Findings distinguish PR-specific regressions from existing gaps. All code references below point to the inspected PR head.

### Cited findings

#### F1 — P1 / high confidence: shared `exports` schema rejects Durable Objects and Workflows

- **2026-07-04:** Cloudflare added declarative Durable Object class lifecycle entries in `exports`, with `type: "durable-object"`, storage selection, and created/deleted/renamed/transferred states. The published date is July 4; the source filename says June 30. **2026-09-24:** Workflow declarations added `type: "workflow"`, `name`, `limits`, `schedules`, and `default_retention`. **2026-09-27:** Workflows declared this way became callable locally through `ctx.exports.MyWorkflow` in Wrangler, Vite, and Vitest. [DO announcement](https://developers.cloudflare.com/changelog/post/2026-06-30-declarative-do-class-exports/); [Workflow declaration](https://developers.cloudflare.com/changelog/post/2026-09-24-workflow-exports/); [local Workflow loopback](https://developers.cloudflare.com/changelog/post/2026-09-27-workflow-ctx-exports/).
- **Parsing:** [src/config.ts:8–9,110–120,139–143][config] restricts `exports` types to `worker` and calls that validator for every config load, even if caching is disabled or absent. A valid `exports.MyWorkflow = {type: 'workflow', name: 'my-workflow'}` failed in a temporary-file probe with `exports.MyWorkflow.type must be "worker"`. The same unconditional branch rejects `durable-object`.
- **Wiring:** [src/env.ts:141–185,187–201][env] only applies legacy DO migrations and builds Workflow bindings from `config.workflows`. [src/worker-thread/thread-env.ts:96–104][thread-env] also only builds `config.workflows`. [src/bindings/worker-cache.ts:593–645][worker-cache] builds `ctx.exports` only for classes with the `lopata.WorkerEntrypoint` marker. Accepting the parser shape alone would not provide Workflow exports or DO lifecycle migration semantics.
- **Tests:** [tests/worker-cache-config.test.ts:34–47][cache-config-test] tests rejection of arbitrary export types but does not test coexistence with official DO/Workflow export types. [tests/worker-cache-config.test.ts:69–117][cache-config-test] positively demonstrates WorkerEntrypoint loopbacks, so `ctx.exports` is **partial**, not wholly missing as [FEATURES.md:31–35,133–140][features] currently implies.
- **Assessment:** the unconditional valid-config rejection is introduced by the PR's cache validation and should be considered separately from the larger follow-up to implement DO/Workflow export wiring. Cloudflare account-wide transfer coordination remains cloud-only; local class/storage lifecycle and Workflow loopbacks are local contracts.

#### F2 — P2 / high confidence: `secrets.required` local behavior is missing

- **2026-03-25:** The new `secrets.required` property makes `.dev.vars`, `.env`, and shell-secret loading selective. Additional file keys are excluded, required shell-only keys can supply bindings, and missing required values cause a local warning. Deployment validation/type generation are separate cloud/tooling concerns. The filename is March 24, but frontmatter and published date are March 25. [announcement](https://developers.cloudflare.com/changelog/post/2026-03-24-secrets-config-property/); [configuration reference](https://developers.cloudflare.com/workers/wrangler/configuration/#secrets-configuration-property).
- **Parsing and wiring:** [src/config.ts:6–105,110–120][config] has no `secrets` contract and retains unknown raw config properties without implementing them. [src/env.ts:82–104][env] loads every file key, then considers shell values only for already loaded `vars`/file keys. This resolver is shared by main, user-worker, and DO env builders; [src/worker-thread/thread-env.ts:68][thread-env] calls it directly.
- **Observed probe:** with `secrets.required = ['NEEDED']` and `.dev.vars` containing `NEEDED=yes` and `EXTRA=unexpected`, resolved env contained `EXTRA`. Removing the file and setting shell `NEEDED=shell-only` did not create the required binding. There is no missing-secret warning in that resolver.
- **Tests:** [tests/env-vars.test.ts:66–128,143–176][env-vars-test] cover the previous unfiltered contract and declared-name shell handling, not `secrets.required`.

#### F3 — P1 for new config forms, otherwise P2 / high confidence: automatic resource provisioning configs do not work locally

- **2025-10-24:** Wrangler 4.45.0 added local and remote automatic provisioning for declarations that contain only a binding: `kv_namespaces: [{binding: 'MY_KV'}]`, `d1_databases: [{binding: 'MY_DB'}]`, and `r2_buckets: [{binding: 'MY_R2'}]`. Local development must work before account IDs are written back. Cloud account provisioning itself is outside Lopata's role. [announcement](https://developers.cloudflare.com/changelog/post/2025-10-24-automatic-resource-provisioning/).
- **Parsing:** [src/config.ts:20–26][config] still requires KV `id`, R2 `bucket_name`, and D1 `database_name/database_id` at the type level, but raw JSON parsing does not validate their absence.
- **Wiring:** [src/bindings/stateless-env.ts:74–94][stateless-env] passes missing `kv.id` to `SqliteKVNamespace`, missing `r2.bucket_name` to `FileR2Bucket`, and missing `d1.database_name` to `openD1Database`, with no local derived identity. [src/bindings/kv.ts:29–33,77–79][kv] stores and uses that namespace unchanged.
- **Observed probe:** loading a minimal KV declaration succeeded, but its first `put()` failed with `NOT NULL constraint failed: kv.namespace` against an in-memory migrated DB. KV is reproduced. R2/D1 consequences are inferred from the wiring; do not claim their exact failure mode without separate probes.

#### F4 — P2 / high confidence: Vite programmatic config and configless assets-only sites are unsupported

- **2025-12-08:** Cloudflare Vite added `config` as an object or customizer callback, including config-only auxiliary Workers. It also made the Wrangler file optional for assets-only Vite sites. **2026-01-20:** auxiliary Workers became fully supported with framework build output, requiring Vite 7+. [programmatic config announcement](https://developers.cloudflare.com/changelog/post/2025-12-08-vite-programmatic-config/); [configless assets announcement](https://developers.cloudflare.com/changelog/post/2025-12-08-vite-optional-config/); [auxiliary frameworks](https://developers.cloudflare.com/changelog/post/2026-01-20-auxiliary-workers/).
- **API:** [src/vite-plugin/index.ts:8–24,38–50][vite-index] has no `config` customizer; auxiliaries require `configPath`. It forwards a file path, environment name, and host settings only.
- **Startup:** [src/vite-plugin/dev-server-plugin.ts:426–443][vite-dev] always loads a config file and explicitly rejects a main Worker without `main`. This is not a missing assets implementation: the CLI already supports assets-only Workers, [src/generation-manager.ts:59–70,212–238][generation-manager], and [FEATURES.md:925–945][features] documents that support.
- **Auxiliary caveat:** [src/vite-plugin/dev-server-plugin.ts:559–575][vite-dev] runs auxiliaries through native Bun imports instead of Vite's transforms; [src/vite-plugin/index.ts:15–21][vite-index] explicitly documents the limitation. Service binding wiring exists, but equivalent aliases/plugin transforms/build output were not verified. This is existing partial support, not a claim that auxiliaries are entirely absent.

#### F5 — P2 / high confidence: `CLOUDFLARE_ENV` does not select environments

- **2025-11-09:** Wrangler added `CLOUDFLARE_ENV`; explicit `--env` has precedence. The setting also coordinates environment selection in the Cloudflare Vite plugin. [announcement](https://developers.cloudflare.com/changelog/post/2025-11-09-cloudflare-env-variable/).
- **CLI:** [src/cli.ts:9–27][cli] only obtains an env name from `-e/--env`. [src/cli/context.ts:86–101][cli-context] uses the supplied env name directly. A probe with shell `CLOUDFLARE_ENV=staging` produced `createContext(undefined, undefined).envName === undefined`.
- **Vite:** [src/vite-plugin/dev-server-plugin.ts:426–430,559–563][vite-dev] does not pass any env name to `loadConfig()` for main or auxiliary Workers. `viteEnvironment.name` selects Vite's module environment, not Wrangler's named config environment.
- **Related present-day reference:** Cloudflare's Vite API also resolves `CLOUDFLARE_VITE_WRANGLER_CONFIG_PATH` between the explicit path and autodetection; Lopata's same startup branch skips that variable. The current reference proves the contract, but this research did not establish its original introduction date, so it is not independently counted as an annual announcement. [Vite API](https://developers.cloudflare.com/workers/vite-plugin/reference/api/).
- **Matrix correction:** [FEATURES.md:1205–1216][features] claims `.dev.vars.<environment>` support. [src/env.ts:82–104][env] only reads `.dev.vars` or `.env` and receives no selected environment name. That matrix claim should not be used to infer correct environment-specific secret loading. Its original introduction date is not established here; this is an existing documentation/implementation discrepancy, not a separate dated annual finding.

#### F6 — P2 / high confidence: RSC `childEnvironments` are not wired

- **2026-02-11:** Vite's new `viteEnvironment.childEnvironments` embeds multiple separate module graphs in one Worker and integrates with `@vitejs/plugin-rsc`. [announcement](https://developers.cloudflare.com/changelog/post/2026-02-11-vite-plugin-child-environments/).
- [src/vite-plugin/index.ts:12,38–50][vite-index] accepts/forwards a name only. [src/vite-plugin/config-plugin.ts:40–71][vite-config] creates one environment. [src/vite-plugin/modules-plugin.ts:23–32][vite-modules] resolves Cloudflare modules only in that environment. There is no child-environment mapping or bridge in this startup flow. Existing React Router-specific middleware support is not evidence of RSC support.

#### F7 — P2 / high confidence for wiring, medium confidence for all Bun versions: default `.sql` imports have wrong CLI contents

- **2026-01-20:** Wrangler and Vite automatically import `.sql` as JavaScript strings containing the file contents, including Drizzle migrations, without custom module rules. [announcement](https://developers.cloudflare.com/changelog/post/2026-01-20-sql-module-rule/).
- CLI startup uses native Bun imports via [src/generation-manager.ts:131–142][generation-manager] and [src/worker-thread/entry.ts][thread-entry]. [src/virtual-modules.ts:19–106][virtual-modules] registers specific virtual Cloudflare modules; it provides no SQL module loader. [src/vite-plugin/modules-plugin.ts:7–11,27–32][vite-modules] likewise only resolves the named virtual modules. The Wrangler config type does not expose `rules`, [src/config.ts:6–105][config].
- **Observed Bun 1.3.14 probe:** `import './example.sql'` returned the absolute file path string, not `SELECT 1;\n`. That can quietly pass a string type check and then fail as migration SQL. The CLI path is concrete; Vite/Drizzle and Bun 1.4.2 were not exercised, so avoid extending the reproduced result to every backend/version.

#### F8 — P2 / high confidence: the 1,000 subrequest ceiling ignores the new configurable limit

- **2026-02-11:** paid Workers moved to a default 10,000 subrequests, configurable to 10 million using `limits.subrequests`. Free-plan restrictions remain. The headline “no longer limited to 1000” does not mean unlimited. [announcement](https://developers.cloudflare.com/changelog/post/2026-02-11-subrequests-limit/); [limits reference](https://developers.cloudflare.com/workers/wrangler/configuration/#limits).
- [src/config.ts:6–105][config] has no top-level `limits` field; [src/worker-thread/thread-env.ts:144–182][thread-env] enforces `MAX_SUBREQUESTS = 1000` for service/DO RPC proxy fetch/method calls. [src/bindings/service-binding.ts:22–32,78–81,111–123][service-binding] also defaults to 1,000. [src/env.ts:228–231][env] does not forward configured limits to service bindings.
- **Assessment:** excessive strictness locally can reject an application allowed on paid Workers. This is not a request to emulate billing/account plans; honor an explicit local `limits.subrequests` contract, or document the hard ceiling. Other binding calls and global fetch are not proven to use this same counter, so do not call it a complete quota emulator.

Cloud policy enforcement, account defaults, and domain protection are separate hosted services. [announcement](https://developers.cloudflare.com/changelog/post/2026-08-14-workers-access/).
- [src/config.ts:6–105][config] has no Access config contract. [src/execution-context.ts:24–53][execution-context] and [src/worker-thread/execution-context.ts:31–56][thread-context] have no `access` field. [src/bindings/worker-cache.ts:593–605][worker-cache] attaches cache/loopbacks, not Access.

#### F10 — P2 / high confidence: tracing API coverage is broader than the deferred `getActiveSpan()` gap

- **2026-06-16:** `enterSpan()` and `setAttribute()/isTraced` shipped. **2026-07-28:** `startActiveSpan()` and explicit `span.end()` added streaming/lifetime instrumentation. **2026-09-25:** `startSpan()`, `getActiveSpan()`, `recordException()`, `setAttributes()`, and chainable attribute setters were added. These are runtime APIs, not merely hosted observability UI. [June announcement](https://developers.cloudflare.com/changelog/post/2026-06-16-custom-spans/); [July announcement](https://developers.cloudflare.com/changelog/post/2026-07-28-start-active-span/); [September announcement](https://developers.cloudflare.com/changelog/post/2026-09-25-custom-span-apis/).
- [src/tracing/span.ts:16–21,70–76,145–150][span] exposes only `tracing.enterSpan`; handles expose `setAttribute` returning void and `isTraced`. The internal function named `startSpan` at lines 127–129 takes Lopata's callback/options contract and is not exported on the Cloudflare namespace. Thus its presence is not support for Cloudflare's new `tracing.startSpan(name)`.
- **Wiring caveats:** [src/virtual-modules.ts:44–52][virtual-modules] exports native `tracing`, while [src/vite-plugin/modules-plugin.ts:44–81][vite-modules] does not export `tracing` at all. [src/execution-context.ts:29–30][execution-context] exposes `ctx.tracing`; [src/worker-thread/execution-context.ts:31–56][thread-context] does not. [src/worker-thread/entry.ts:227–231][thread-entry] supplies `WorkerExecutionContext` to the dispatcher. Therefore even the existing June API is not uniformly available through every documented entry path.
- **Already acknowledged in part:** [CLOUDFLARE-COMPATIBILITY.md:103][compat-review] defers `getActiveSpan()` alone. The annual report should list the whole expanded contract and backend wiring limits. Global/module researchers should cross-check this finding.

It accepts the same tags/pathPrefixes/purgeEverything options and per-entrypoint scope/result as purge. This is a local cache API contract. [announcement](https://developers.cloudflare.com/changelog/post/2026-09-29-workers-cache-invalidate/).

The PR's July cache implementation therefore does not cover a September API already inside the review window. Binding researchers should own the detailed HTTP/cache-state implementation review.
- Distinguish this from **2026-09-28** account/CDN cache invalidation: the CDN Purge API and Cache Reserve behavior depend on Cloudflare infrastructure; they are not the same interface. [CDN announcement](https://developers.cloudflare.com/changelog/post/2026-09-28-cache-invalidation/).

Their Worker-facing binding names and methods still need a deliberate local mock or remote proxy contract. #### F13 — P2 / high confidence: Hyperdrive's local connection-string environment override is ignored

- **2025-12-04:** local Hyperdrive support explicitly includes `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_<BINDING_NAME>` alongside `localConnectionString`, with direct remote/TLS database development while code remains local. #### F15 — P2 / high confidence: compatibility dates and disable flags are largely metadata

- **2025-11-17:** `enable_ctx_exports` becomes default by compatibility date; `disable_ctx_exports` opts out. **2026-08-04:** Node compatibility becomes date-default, with `no_nodejs_compat` and `no_nodejs_compat_v2` required to opt out. These are behavior gates, not config syntax alone. [ctx.exports flag source](https://github.com/cloudflare/cloudflare-docs/blob/03f58703df62daa18049b7e0043bb6e25c659670/src/content/compatibility-flags/enable-ctx-exports.md); [Node default announcement](https://developers.cloudflare.com/changelog/post/2026-08-04-nodejs-compat-default/).
- [src/config.ts:18–19][config] stores date/flags. The only config-sensitive global setup found was [src/setup-globals.ts:13–16][setup-globals], which implements the explicit modern-crypto flag. [src/bindings/worker-cache.ts:604,627–645][worker-cache] attaches WorkerEntrypoint loopbacks unconditionally and recognizes no DO/Workflow loopback classes. Neither disable flag nor date affects this path.
- [src/bindings/worker-loader.ts:28–38,102–108][worker-loader] requires a `compatibilityDate` in the public dynamic-worker contract but sends only `compatibilityFlags`, not the date, in the runtime initialization message. Native Bun Node APIs are generally present regardless of a Worker's compatibility date; that does not emulate no-Node opt-out or Cloudflare's non-functional Node stubs.
- **Assessment:** do not label each new flag unsupported merely because the flag is not interpreted. Bun may natively match the new behavior. The specific confirmed configuration gap is lack of date/opt-out selection. The complete annual flag inventory below is a handoff checklist for globals/binding researchers to test actual semantics.

### Inferences

- Accepting valid shared `exports` types without accidentally treating them as cache declarations is a narrow PR review issue. Full DO/Workflow lifecycle support is a larger follow-up. F1 deliberately separates those conclusions.
- Local-relevant additions are often hidden in deployment-sounding announcements: ID-free resource config, Workflow exports, DO exports, required-secret filtering, and Container runtime selection all change local startup or user-code contracts.
- The annual scope adds October 2025–March 2026 material absent from the existing review. F3–F8 and F13 are particularly relevant earlier-window additions.

### Gaps

- No source/PR changes were made. No full test suite was run. Temporary probes used **Bun 1.3.14**, not the Bun 1.4.2 CI version mentioned in the existing review. Probe results are precise to that runtime.
- SQL import behavior under Vite/Bun 1.4.2, R2/D1 ID-free failure modes, RSC frameworks, Docker FUSE, Container dynamic image selection, and Hyperdrive TLS were not exercised end to end.

## 2. What should be counted as platform-only, existing local support, or separate research?

### Takeaway

Cloud-hosted deployment, billing, identity enforcement, resource geography, and account observability do not require local emulation. Their config can still matter when it creates bindings or supplies behavior to user code. Existing building blocks are partial support, not evidence of full contract equivalence.

## 3. What proves annual chronological coverage, and what are its limits?

### Takeaway

The source-driven index contains **388 dated official changelog entries across 32 product folders**, covering every month from October 2025 through October 2026. It additionally inventories compatibility flag dates and verifies the 20 blog URLs already referenced by the PR review. It is a systematic selected-ecosystem index, not a claim that every Cloudflare announcement or every workerd change appears in the changelog.

### Cited findings

- Primary index source: GitHub API recursive tree for `cloudflare/cloudflare-docs` **`production`** (not `main`). `truncated: false`; **16,011 paths**. The inspected `production` commit was **`03f58703df62daa18049b7e0043bb6e25c659670`**, and the branch API's underlying Git tree SHA was `cb1490aec9203887489b3dd329b2341517b5bcc7`. [snapshot](https://github.com/cloudflare/cloudflare-docs/tree/03f58703df62daa18049b7e0043bb6e25c659670/src/content/changelog); [GitHub tree API](https://api.github.com/repos/cloudflare/cloudflare-docs/git/trees/03f58703df62daa18049b7e0043bb6e25c659670?recursive=1).
- Downloaded complete MD/MDX bodies for the selected ecosystem products and extracted each entry's `date` frontmatter. Older filenames were also scanned back to January 2025 to catch publication/filename mismatches. Notably `workers-vpc/2025-09-25-workers-vpc.mdx` has **2025-11-05** frontmatter and belongs inside this review. No matching selected-product changelog entries were dated October 3–5, 2026 in this snapshot; that is not evidence of no announcements on those days.
- Canonical changelog URLs use **`/changelog/post/<filename-slug>/`**. A live fetch of Workflow exports confirmed the canonical URL, visible September 24 date, and JSON-LD `datePublished`. Body links also use that canonical route. The index below links every source by that route, not search snippets.
- All existing review blog URLs were retrieved and their JSON-LD `datePublished` values extracted. The blog supplement below records those dates, including Workers Cache July 6 and modern crypto October 1. These are blog publications; they are not necessarily API shipping dates. Workflow saga, for example, has a June 5 changelog and a June 25 engineering blog. [saga changelog](https://developers.cloudflare.com/changelog/post/2026-06-05-saga-rollbacks/); [saga blog](https://blog.cloudflare.com/rollbacks-for-workflows/).
- Code review read `CLAUDE.md`, `CLOUDFLARE-COMPATIBILITY.md`, `FEATURES.md`, config parsing, CLI/Vite startup, main/thread env builders, dispatcher/contexts, shared stateless binding wiring, related config/env/cache tests, and referenced platform adapters. Local checks were read-only except temporary files under `/tmp/opencode` and this required notes file.

### Inferences

- The source index substantially broadens the existing April–October blog-based review: December Vite config, October ID-free binding provisioning, March required secrets, July DO exports, September Workflow exports, September cache invalidation, and July/September tracing additions are independently verifiable.
- Compatibility flags have separate **sort/introduction dates** and **default enable dates**. These must not be conflated. `nodejs_compat` has an old sort date but an August 4, 2026 default; WebSocket auto-close has March 10 sort date and April 7 default; modern crypto is opt-in with no default enable date.

### Gaps and limitations

- Product selection is explicit. Included: Workers, Workers AI, Workers for Platforms, Workers VPC, Workflows, Durable Objects, KV, R2, D1, Queues, Hyperdrive, Images, Stream/Media, AI Gateway, AI Search, Browser Run, Containers, Sandbox, Vectorize, Artifacts, Flagship, Email Service, Web Search, Agents, Agent Lee, Basin/Pipelines/Catalog/SQL, Mesh, Cache, and SSL. Some broad Cache/SSL/Agents entries are intentionally retained as cloud-only cross-checks.
- There is no standalone `wrangler` or `vite` product folder in the retrieved changelog tree; relevant tooling announcements are chiefly under Workers. No standalone `secrets-store` changelog folder was found. Its beta announcement in the SSL folder predates the interval; this does not establish absence of later Secrets Store changes elsewhere.
- This is not a complete scan of unrelated Zero Trust, billing, networking, rules, Terraform-provider, API SDK, or dashboard product folders, nor the full Workers SDK release history or workerd commit history. Current reference docs can contain changes with no dated announcement; such contracts are labeled undated here.
- MD/MDX bodies were fetched from `production` during the run; branch commit/tree was checked afterward and matched the initial tree response SHA. The snapshot link pins the coverage source. It is not a historical Git reconstruction of each release's original text, so later editorial updates to dates/text are possible.
- No tests were added and no repo source was edited. The temporary probe reproduced valid-export rejection, required-secret filtering/shell-only omissions, `CLOUDFLARE_ENV` omission, minimal-KV failure, and native SQL path import behavior. Existing test source was inspected; existing suite results quoted in `CLOUDFLARE-COMPATIBILITY.md` were not independently rerun.
